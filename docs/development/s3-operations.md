# Durable S3 operations / Operações S3 persistentes

Decision / Decisão: [ADR-0029](../decisions/ADR-0029-minimal-workspace-operations.md). This page describes the current implementation; execution evidence is separate. / Esta página descreve a implementação atual; evidência de execução é separada.

## English

Responsiveness refinement: the initial local-state check is scheduled after 150 ms (immediately for a new visible notification), with bounded backoff to two seconds, no overlapping poll cycles and no hidden-document polling. This supersedes the fixed two-second startup interval below. Confirmed action results appear immediately; compatible service listings refresh once through checked read fragments, preserving filter/cursor/scroll/focus, with one queued follow-up if completion races a read. No emulator health polling or mutation retry is introduced. Failed refresh keeps the existing listing with explicit failure feedback. Native navigation remains for a different destination and canonical fallbacks. Notifications follow ADR-0034: compact, dismissible, confirmed success expires after five visible seconds with hover/focus/visibility pause, other outcomes remain until dismissed; updates do not reload the page.

Version-action availability: listing a `null` version does not establish that permanent version deletion is available. The UI reads bucket versioning and offers removal only for Enabled/Suspended status. A never-versioned bucket retains ordinary object deletion; direct version-delete entry is refused before creating a journal record, without an operation link. Protocol/permission failures and fresh worker rechecks remain authoritative; versioning status alone is not a universal compatibility guarantee.

2026-10-27 verification: Java 25/Maven with local MiniStack passed 186 tests, no failures/errors/skips (`work/version-availability-maven.log`). Four browser navigation cases passed across both languages/themes and 390/1366/1440 px (`work/version-availability-browser.log`); local frontend checks passed. A browser/HTTP probe confirmed no delete-version action for a never-versioned fixture and a 409 HTML refusal without an operation link. No new application image/container suite was run.

The canonical bucket/object deletion URLs prepare a durable server inventory. Preparation reads S3 and records intent locally; it never deletes objects. Review contains the exact bucket/key, one consequence and one submit. Only bucket deletion requires its exact name. POST starts the reviewed operation; duplicate submissions return its existing state. CSRF remains mandatory. New objects are never added to an already reviewed inventory.

`/operations` lists local records; `/operations/{id}` shows counts and paginated item outcomes. `/{id}/review` presents confirmation; protected POST `/{id}/start`, `/{id}/interrupt` and `/{id}/resume` control it. `/{id}/state` reads local status only. The browser checks active visible areas every two seconds, without querying S3 health. Closing the browser leaves submitted work running. A server restart marks work interrupted and any in-flight item uncertain. Resume reconciles absence where possible and never repeats an uncertain copy/move or ordinary versioned deletion. A request already sent cannot be cancelled or rolled back.

The H2 file store lives under `.stackemu/operations` by default and is excluded from Git. Run one application instance against that file. Back up the directory only with the application stopped. Do not edit the database or delete its files to resolve an uncertain operation. The persistence adapter owns JDBC; application contracts have no SDK, HTTP or database dependency. Schema version 2 adds an endpoint/region fingerprint; migration preserves existing records but older unbound inventories require a new review. Commits use `WRITE_DELAY=0` before remote writes. Changing the configured endpoint cannot authorize an old inventory against the new destination.

The worker processes one operation at a time and claims both source and destination buckets. Each item's intent is committed before its remote request. Individual requests use an owned no-retry client. Versioned inventory includes versions and delete markers; permanent removal targets explicit version IDs. Ordinary object deletion follows S3 delete-marker semantics. Empty-only bucket deletion does not become cleanup when content appears. Prefix cleanup is bounded to its exact slash-terminated prefix. Versioning changes, permission failures, retention restrictions, unsupported protocol and new remaining content prevent a successful bucket deletion.

Copy/move addresses one object within the configured endpoint, streaming through an owned temporary file with bounded size. Content bytes, type and supported metadata are retained. Move copies before deleting the source, so partial/uncertain outcomes are possible. Existing destinations require explicit replacement and conditional writes. Upload defaults to its original filename; conflict offers another name or reviewed replacement. Preserve the original extension when choosing another name. The upload must be selected again after a conflict; its body is not retained by the GUI.

`/s3/versions` displays versions, including keys hidden by delete markers; `/s3/object-metadata` provides metadata outside the drawer. `/s3/transfer` prepares copy/move. `/s3/share` generates a download URL only after an explicit POST, default 15 minutes, maximum 60 minutes or the smaller known credential lifetime. The link grants download access to its holder and is not persisted in operations, logs or browser notification storage. Actual expiry enforcement belongs to the emulator; compatibility must be verified rather than assumed.

Successful short actions close and return a dismissible message. A single-use tab-session notification record transfers only generic feedback, an operation ID and timestamp across navigation; it contains no file contents, credentials or signed URL. This explicitly supersedes earlier bans on all browser storage for feedback, while preferences remain URL-based. Operation details and technical policies do not appear as dialog expanders. Native forms/pages remain practical fallbacks.

| Setting                              | Default                | Purpose                                                                |
| ------------------------------------ | ---------------------- | ---------------------------------------------------------------------- |
| `STACKEMU_OPERATIONS_PATH`           | `.stackemu/operations` | Embedded database basename                                             |
| `STACKEMU_OPERATIONS_MAX_STORAGE`    | `268435456`            | Admission limit in bytes for the database file; not a filesystem quota |
| `STACKEMU_OPERATIONS_RETENTION_DAYS` | `30`                   | Completed/failed/partial history retention, pruned when preparing work |
| `STACKEMU_OPERATIONS_PAGE_SIZE`      | `100`                  | Inventory pages, clamped to 1–100; UI pages contain 50 items           |
| `STACKEMU_OPERATIONS_MAX_TRANSFER`   | `67108864`             | Maximum individual copy/move bytes                                     |
| `STACKEMU_OPERATIONS_CALL_TIMEOUT`   | `PT30S`                | Per-call timeout, ISO-8601 duration from 1 second to 5 minutes         |

Queue admission is bounded to 32 tasks, protocol XML to 1 MiB, inventory preparation to ten minutes, and each operation-client call defaults to 30 seconds with bounded socket/connect timeouts. The call deadline is configurable from 1 second to 5 minutes using an ISO-8601 duration. These are implementation limits, not throughput claims or the old 25-item product cap. Upload retains its independently configured size/body limits. A full disk can still reject journal updates; inspect the resulting operation before any manual repetition. `.stackemu` contains resource names/history and should be treated as local project data.

## Português

Refinamento de fluidez: primeira consulta de estado local após 150 ms (imediata para novo aviso visível), com backoff limitado a dois segundos, sem ciclos sobrepostos ou consultas em documento oculto. Substitui o intervalo inicial fixo abaixo. Resultados confirmados aparecem imediatamente; listagens compatíveis atualizam por fragmentos verificados, preservando filtro/cursor/rolagem/foco e uma atualização posterior se a conclusão coincidir com leitura em andamento. Sem polling de saúde ou retry de mutações. Falha mantém listagem anterior e aviso explícito. Navegação nativa preservada para destino diferente/fallback. Avisos seguem ADR-0034: compactos, dispensáveis, sucesso expira em cinco segundos visíveis com pausas por mouse/foco/visibilidade, demais estados permanecem até dispensa; atualização sem recarga.

Disponibilidade da ação: listar versão `null` não comprova exclusão permanente disponível. A interface consulta o versionamento e oferece remoção somente em estado Enabled/Suspended. Bucket nunca versionado mantém exclusão comum; entrada direta de exclusão de versão é recusada antes de criar registro, sem link de operação. Falhas de protocolo/permissão e novas verificações do worker continuam valendo; o estado de versionamento não garante compatibilidade universal.

Verificação em 2026-10-27: Java 25/Maven com MiniStack local aprovou 186 testes, sem falhas/erros/skips. Quatro casos de navegação passaram nos dois idiomas/temas e em 390/1366/1440 px; checks frontend locais aprovados. Probe de navegador/HTTP confirmou ausência da ação em fixture nunca versionada e recusa HTML 409 sem link de operação. Sem nova imagem da aplicação ou suíte em contêiner; logs indicados na seção inglesa.

As URLs canônicas de exclusão de bucket/objeto preparam inventário persistente no servidor. Essa preparação lê S3 e registra intenção localmente, sem excluir recursos. A revisão apresenta alvo exato, consequência curta e envio explícito. Somente exclusão de bucket exige seu nome exato. POST inicia a operação revisada; envios duplicados devolvem seu estado existente. CSRF é obrigatório. Objetos novos não entram silenciosamente no inventário autorizado.

`/operations` lista registros locais; `/operations/{id}` mostra contagens/resultados paginados. `/{id}/review` confirma; POSTs protegidos `/{id}/start`, `/{id}/interrupt` e `/{id}/resume` controlam execução. `/{id}/state` lê somente o registro local. O navegador acompanha áreas visíveis/ativas a cada dois segundos, sem consultar saúde S3. Fechar navegador mantém trabalho enviado. Reinício do servidor marca interrupção e itens em voo como incertos. Retomada reconcilia ausência quando possível, sem repetir cópia/movimentação incerta ou exclusão comum versionada. Não há cancelamento/desfazer de requisição já enviada.

H2 usa `.stackemu/operations`, ignorado pelo Git. Uma instância por arquivo; backup com aplicação parada. Não editar/apagar banco para resolver incerteza. Adaptador concentra JDBC; aplicação não depende de SDK/HTTP/banco. Schema 2 adiciona fingerprint de endpoint/região e preserva registros antigos, cujos inventários sem vínculo exigem nova revisão. Commits usam `WRITE_DELAY=0` antes da escrita remota; mudar endpoint não autoriza inventário antigo no destino novo.

O worker executa uma operação por vez e reserva buckets de origem/destino. Persiste intenção de cada item antes da requisição, com cliente próprio sem retries. Inventário versionado inclui versões/delete markers; exclusão permanente usa versionId exato. Exclusão comum segue semântica S3 de delete marker. Exclusão de bucket vazio não vira limpeza se aparecer conteúdo. Limpeza de pasta limita-se ao prefixo exato terminado em barra. Mudanças de versionamento, permissões, retenção, protocolo incompatível ou conteúdo novo impedem concluir exclusão do bucket.

Cópia/movimentação trata objeto individual no endpoint configurado, transmitindo por temporário próprio limitado. Preserva bytes, tipo e metadados suportados. Mover copia antes de excluir a origem, podendo terminar parcial/incerto. Destino existente exige substituição explícita e escrita condicional. Upload usa nome original; conflito oferece outro nome ou substituição revisada, mantendo extensão. Após conflito é necessário selecionar novamente o arquivo; a GUI não retém seu conteúdo.

`/s3/versions` inclui versões ocultas por delete markers; `/s3/object-metadata` apresenta metadados fora do drawer. `/s3/transfer` prepara cópia/movimentação. `/s3/share` gera URL de download por POST explícito, padrão 15 minutos, máximo 60 ou validade conhecida menor das credenciais. Quem possui o link pode baixar; URL não entra em operações/logs/armazenamento de avisos. O emulador aplica expiração; não presumir compatibilidade sem teste.

Ações curtas concluídas fecham com aviso dispensável. Registro de sessão da aba, consumido uma vez, transporta apenas aviso genérico, ID da operação e timestamp entre navegações; sem conteúdo, credenciais ou URL assinada. Substitui a proibição histórica de todo armazenamento no navegador para esse feedback; preferências continuam por URL. Diálogos não têm relatórios/expansores técnicos; páginas/formulários canônicos seguem como fallback prático.

As configurações da tabela acima controlam caminho, admissão do arquivo (256 MiB), retenção terminal de 30 dias, páginas de inventário de 1–100 e transferência individual de 64 MiB. Páginas da UI têm 50 itens. Fila de 32 tarefas, XML de 1 MiB, preparação de até dez minutos e chamadas com padrão de 30 segundos são limites técnicos; o prazo é configurável de 1 segundo a 5 minutos em duração ISO-8601. Não são promessa de desempenho nem limite antigo de 25 itens. Upload mantém limites independentes. Disco cheio pode impedir registros; verificar a operação antes de repetir manualmente. Histórico contém nomes de recursos e merece tratamento de dado local do projeto.
